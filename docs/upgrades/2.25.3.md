## Data-Clearing Migration — Read Before Updating

Upstream retired the per-model OAuth 429 review blocks. `backend/migrations/399_remove_oauth_429_model_blocks.sql`
runs when the new image starts:

```sql
WITH changed AS (
    UPDATE accounts
    SET extra = extra - 'oauth_429_model_blocks',
        updated_at = GREATEST(clock_timestamp(), updated_at + INTERVAL '1 microsecond')
    WHERE extra ? 'oauth_429_model_blocks'
    RETURNING id
)
INSERT INTO scheduler_outbox (event_type, account_id)
SELECT 'account_changed', id FROM changed;
```

- 它只移除 `accounts.extra` 里已废弃的 `oauth_429_model_blocks` 键，并为每个受影响账号写入一条
  `scheduler_outbox` 刷新事件。不是 `DROP`/`TRUNCATE`/`DELETE FROM`，`docs/UPGRADING.md` 5.3 的关键字扫描抓不到，
  是通读迁移正文和 v2.25.2 发布说明发现的。
- **Model Guard 不受影响。** 巡检屏蔽用的是另一个键 `codex_eval_inspection_blocked_models`，迁移不碰它。
- 内置更新通道不建快照，回退镜像不会恢复已清除的屏蔽记录（上游发布说明同样注明）。上游已把这些记录视为废弃，
  2.25.3 的代码不会再读取，需要留档才导出：

```bash
# 先看有多少账号还带着这个键
docker exec -i sub2api-postgres psql -U sub2api -d sub2api -Atc \
  "select 'accounts_with_blocks='||count(*) from accounts where extra ? 'oauth_429_model_blocks';"

# 需要留档时导出（只导 id 和 extra）
mkdir -p /root/backups
docker exec -i sub2api-postgres psql -U sub2api -d sub2api -Atc \
  "select json_agg(json_build_object('id', id, 'extra', extra)) \
     from accounts where extra ? 'oauth_429_model_blocks';" \
  > "/root/backups/oauth-429-model-blocks-2.25.0-$(date +%Y%m%d-%H%M%S).json"
```

> 以上两条查询本次没有在服务器上演练（开发机不执行远程命令）。

   rollback data directory is used.

## Rollback Path

- Previous image remains published as `ghcr.io/ericzhouyihe/sub2api-codex-guard:2.25.0`
  (`sha256:d8ba0256...`), verified resolvable in GHCR after the 2.25.3 publish.
- To roll back, pin the compose image to `:2.25.0` and recreate `sub2api`:
  ```bash
  sed -i -E "s#image: ghcr.io/ericzhouyihe/sub2api-codex-guard:.*#image: ghcr.io/ericzhouyihe/sub2api-codex-guard:2.25.0#" docker-compose.yml
  docker compose up -d sub2api
  ```
- Docker mode has no in-page rollback (`DOCKER_UPDATE_UNSUPPORTED`) and creates no local data
  snapshot. Watchtower cleanup means the old image is not kept on the server.
- An image rollback does not reverse the 2.25.3 migrations: the added columns stay, and cleared
  `oauth_429_model_blocks` records are gone. The three additive columns have defaults or allow NULL, so the
  2.25.0 image is expected to start on the migrated schema; this rollback was not exercised.
