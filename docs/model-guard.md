# 模型哨兵 / Sub2API Model Guard

本分支将 [Nanboom233/codex-candy-eval](https://github.com/Nanboom233/codex-candy-eval) 的糖果测试、指纹检测、历史记录与自动巡检移植到 `ranxi2001/sub2api`，不是覆盖式安装器，也不替换本 fork 的质量运维功能。

## 功能范围

- 后台「模型哨兵」入口：`/admin/codex-eval`，内嵌同源页面 `/codex-eval`。
- 糖果测试：单账户/筛选后批量、模型与推理强度、每账户 1–10 次、取消任务、回答与用量。
- 指纹检测：内置固定版本 lm-detector 参考库，三组随机挑战、候选排名/概率、原始样本详情。
- 历史记录：按当前分组聚合糖果与指纹记录，按类型、账户、模型搜索；每账户每种类型保留最近 20 条，服务重启后保留。
- 定时巡检：指定分组，按账户类型/订阅/可用性/包含排除通配符筛选；支持单账户退出自动巡检。每轮完成后随机等待配置区间，默认 15–35 分钟，可设相同上下限获得固定等待间隔（不是固定墙上时钟或 cron）。
- 自动处置：可选调整正常/降级优先级；可选限制指定模型，正常后自动恢复；可选 ntfy/Bark 通知。
- 本次**没有引入**原扩展的 Pelican 与 SIWC 测试。目标 fork 原有的同名或其他测试功能保持不动。

## 建议启用顺序

1. 从本分支正常构建并部署到测试环境；使用管理员登录。
2. 在「模型哨兵」选择一个小分组，先手动运行糖果测试与指纹检测，核对回答、指纹候选、请求错误和用量。
3. 在「巡检设置」指定模型、测试方式、账户筛选、等待间隔，先只启用定时巡检观察。
4. 确认误判风险与模型名单后，再开启「模型控制」和/或「优先级调整」，保存设置。它们和定时巡检**默认关闭**，不会因升级而自动修改生产调度。
5. 模型控制中填写**完整、精确的模型 ID**，不能使用通配符。默认名单仅来自上游示例，不代表你的渠道实际支持这些模型；请按自己的模型调整。

糖果巡检在需要改变状态时按配置次数进行一致性确认，默认 3 次；恢复确认之间默认等待 240 秒。指纹巡检一轮包含三组挑战，不套用糖果重复次数。部分/失败/取消的指纹结果、非模型序列、或待测名称不在参考库的结果只作诊断，不自动改变账户；自定义模型仍可手动检测。

## 模型控制：不破坏原有映射

本 fork 的空映射、通配符、别名模式与透传都有自己的语义。直接删除 `model_mapping` 条目无法可靠禁用模型，也可能误删原配置。本移植改为单独的受管限制层：

- 在账户 `extra.codex_eval_inspection_blocked_models` 保存模型哨兵的精确限制列表，不改写原有 credentials 或 model_mapping。
- 调度入口同时检查请求模型与实际映射目标，包含 compact 目标；映射仍遵循一次映射和透传原有语义。限制进入调度缓存投影，并通过已有持久化 outbox 传播。
- 账户普通编辑在数据库行锁内保留最新受管状态；批量编辑不能伪造或用旧表单覆盖该状态。
- 恢复正常只清空模型哨兵的限制，不解除质量运维的模型隔离、Astra 限制、用户白名单、冷却或人工停用。
- 直接巡检沿用账户测试传输，不经过用户调度限制，因此禁用后仍能复测并恢复。
- 关闭「模型控制」停止新增限制，**不会立即清除已存在的限制**；检测恢复正常时仍会清除本功能的限制。不要把关闭开关当成恢复操作。
- 巡检设置改变会取消旧策略的在途轮次；提交模型处置前还会重新检查账户是否仍属于选定范围。

与原 fork 的「质量运维」是两个独立系统。避免让两个系统同时自动调整同一账户的优先级，建议先只启用其中一套优先级控制。

## 存储、鉴权与部署边界

- 巡检设置存于现有设置表（`codex_eval_inspection_*`），不需要数据库表迁移。
- 历史存于应用数据目录下 `codex-eval/history.json`。请将整个数据目录持久化和备份；历史包含账户名称和模型回答，应视为管理数据。旧 schema 会先备份，损坏或未知版本的文件会阻止覆盖保存，并在界面显示错误。
- 只公开静态 UI，不公开管理数据。所有发现/测试/历史/巡检接口沿用现有管理员鉴权与观察者/作用域限制，不能凭 URL 中的 token 调用。内嵌页面每次请求读取本机后台的最新认证信息，不把 JWT 放进 iframe URL。
- `runtime.role=gateway` 请求副本不启动后台巡检。**当前调度器是进程内的，不包含分布式主选举**：多个管理进程共用配置时可能重复检测和消耗额度。建议只在单个管理实例启用本巡检，不要让多个进程共写同一个历史文件。
- 定时循环和自动测试仅在你部署并启用后运行。本次源码合并不会自动部署或操作线上账户。

## 检测局限与成本

- 糖果测试沿用上游的「回答中出现独立数字 21」判断，是简单启发式，不是完整推理判卷，可能误判。
- 指纹是固定候选库上的统计归因，不是模型身份证明；提示词、转发行为、模型更新及未知模型都会影响结果，概率也不是真实性保证。
- 请求错误不等于降级证据；不完整或错误的检测不自动作降级处置。建议先人工观察，再允许自动禁用，并保留恢复测试能力。
- 每次检测使用真实账户向上游发送请求，会消耗 Token/订阅额度；指纹每轮至少三组挑战，失败重试可能增加请求数（上游最多 3 次尝试）。本地回归测试使用模拟响应，不消耗你的上游账户额度。
- 关闭进程会取消巡检并等待工作退出；自定义不遵循 context 的外部传输/钩子可能延长退出时间。

## 本地验证

使用仓库要求的 Go 1.27.4、Node >=22 和兼容现有锁文件的 pnpm。开发机若全局安装了 pnpm 12，旧 `package.json` 中的 `pnpm.overrides` 不再被读取；不要为这个功能随意重写锁文件。可显式使用 pnpm 9.15.4 执行：

```powershell
# frontend 目录
corepack pnpm@9.15.4 install --frozen-lockfile
corepack pnpm@9.15.4 run check:i18n
corepack pnpm@9.15.4 exec vue-tsc -b
corepack pnpm@9.15.4 exec vite build
corepack pnpm@9.15.4 exec vitest run src/utils/__tests__/embedded-url.spec.ts

# 仓库根目录（DOM 测试使用 frontend 已安装的 jsdom）
node --test tests/model-guard-ui.test.cjs tests/model-guard-dom.test.cjs

# backend 目录
$env:GOMAXPROCS='2'
go test -p 1 -tags unit ./internal/codexeval ./internal/service ./internal/repository ./internal/handler/admin -run 'Test(Codex|ModelGuard|Fingerprint|HasStandalone)' -count=1
go build -p 1 -tags embed -trimpath -o bin/model-guard.exe ./cmd/server
```

运行构建前先构建前端，嵌入式产物不提交版本库。上列 Windows 产物用于本地构建验证，不是 Linux 生产部署包。生产发布继续遵循本 fork 原有流程；本分支不自动创建 Release 或合并到 production。
