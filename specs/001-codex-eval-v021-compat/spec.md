# Feature Specification: Codex Eval v0.2.21 兼容版

**Feature Branch**: `001-codex-eval-v021-compat`

**Created**: 2026-11-13

**Status**: Draft

**Input**: User description: "https://github.com/Nanboom233/codex-candy-eval /speckit-specify 不要GitHub自动部署的,我的要求就是能在最新版上使用,他这个项目不是只能19或者20吗,现在想21版本能用,不能简单的做一修改或者变更吗,开源项目"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 在 Sub2API v0.2.21 上安装并使用完整评估功能 (Priority: P1)

作为 Sub2API 管理员，我希望在 **Sub2API v0.2.21** 上安装 Codex 降智测试，并且能正常打开「账户评估」页面、看到糖果/指纹/鹈鹕/SIWC 等测试入口，以便继续使用原项目的完整能力，而不是停留在只支持 v0.2.19 或 v0.2.20 的旧版本。

**Why this priority**: 这是本需求的核心价值；如果 v0.2.21 无法安装或页面不可用，其他功能都没有意义。

**Independent Test**: 在一台装有 Sub2API v0.2.21 的测试环境中执行安装流程，打开「账户评估」页面并运行一次糖果测试；页面、接口和结果均正常。

**Acceptance Scenarios**:

1. **Given** Sub2API 运行版本为 v0.2.21，**When** 管理员执行本项目提供的安装流程，**Then** 安装器完成替换/部署并在健康检查通过后退出，管理后台可正常打开「账户评估」。
2. **Given** 「账户评估」页面已打开，**When** 选择一个可用的 OpenAI OAuth 账号并执行一次糖果测试，**Then** 页面返回正确/错误/失败的明确结果，且不会破坏 Sub2API 原有 API 转发。
3. **Given** 安装完成后 Sub2API 正常处理真实 Codex 请求，**When** 多个账号并发调用，**Then** 原有请求的模型、参数和响应不被插件修改。

---

### User Story 2 - 不依赖 GitHub Actions，也能本地构建安装包 (Priority: P1)

作为项目维护者，我希望从公开源码和一份简短的构建说明出发，在一台普通开发机上构建出可用的 Linux 安装包，不需要 GitHub Actions、云端 CI 或任何自动部署服务。

**Why this priority**: 用户明确要求「不要 GitHub 自动部署」，并且希望这是一个可自行构建、可自由修改的开源项目。

**Independent Test**: 在无 GitHub Actions、无私有 CI 凭据的干净环境中，按 README 的命令完成一次 Linux amd64 构建，得到安装器和对应的服务端二进制。

**Acceptance Scenarios**:

1. **Given** 一台装有必要构建工具的开发机，**When** 维护者按文档执行本地构建命令，**Then** 生成 Linux amd64 安装器与服务端二进制，且不触发任何远程 CI。
2. **Given** 只从本仓库获取源码，**When** 执行构建，**Then** 构建过程不使用仓库外的私密凭据或预编译的私有产物。
3. **Given** 上游 Sub2API 版本变化导致源码无法套用现有兼容变更，**When** 构建失败，**Then** 构建过程明确报错并停止，不产出看似可用的坏包。

---

### User Story 3 - 用尽量小的改动适配新版本 (Priority: P2)

作为开源贡献者，我希望兼容 v0.2.21 的改动集中、可审查、可回退，而不是对原项目做大面积重写，以便后续继续跟随上游维护。

**Why this priority**: 用户强调「不能简单地做一修改或者变更吗」，说明希望低成本适配，而非另起炉灶。

**Independent Test**: 对比 fork 与上游原始项目，统计兼容性改动涉及的文件和范围；所有改动都有说明，且能通过回退到上游版本还原。

**Acceptance Scenarios**:

1. **Given** 上游 codex-candy-eval 的原始代码，**When** 查看本项目的兼容性改动，**Then** 改动集中在兼容适配层、构建脚本与说明文档，不改变原项目的功能设计。
2. **Given** 需要回到上游版本，**When** 维护者移除本项目新增的兼容性改动，**Then** 上游原始功能仍可独立构建（在它原本支持的版本上）。
3. **Given** 开源社区成员阅读改动说明，**When** 对照上游版本，**Then** 能理解每个兼容性变更的原因，而不需要阅读全部业务代码。

---

### User Story 4 - 在更新后的 Sub2API 中保留测试能力 (Priority: P3)

作为长期使用者，我希望 Sub2API 升级/重启后，我仍然可以重新安装或恢复 Codex 评估能力，而不是升级后测试入口直接消失且无法恢复。

**Why this priority**: 这是用户最初遇到的实际问题；版本适配必须给出可重复的升级/恢复路径，避免一次升级后永久失效。

**Independent Test**: 将 Sub2API 从 v0.2.20 升级到 v0.2.21，再执行一次兼容版安装流程，确认「账户评估」恢复可用。

**Acceptance Scenarios**:

1. **Given** Sub2API 已升级到 v0.2.21 且原有补丁版被镜像覆盖，**When** 执行兼容版安装流程，**Then** 「账户评估」页面恢复，历史数据可按文档说明保留或迁移。
2. **Given** 安装失败或新版本不可用，**When** 安装器回滚，**Then** 原 Sub2API 二进制被恢复，服务重新可用。

---

### Edge Cases

- 上游项目没有可用的固定版本标签，或目标 Sub2API v0.2.21 的源码结构与预期不一致时，构建必须停止并给出可操作的错误信息。
- 服务器使用不同容器名称、非 Docker 部署或原生 systemd 部署时，安装流程必须允许选择目标，不能假定容器名一定为 `sub2api`。
- 服务器为 arm64 或非 Linux 平台时，必须明确说明当前安装器支持范围；不支持的平台不能静默产出错误架构的包。
- 安装过程中健康检查超时、容器反复重启或替换后的二进制无法启动时，必须自动恢复原二进制。
- 构建机内存较小、默认文本编码不是 UTF-8 或缺少前端构建工具链时，构建文档必须给出可复现的替代步骤或明确的前置条件。
- Sub2API 后续版本导致兼容性变更不再适用时，本项目不得假装兼容；必须记录已验证版本和失败边界。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 以 **Sub2API v0.2.21** 作为当前明确验证目标，而不是只支持 v0.2.19 或 v0.2.20。
- **FR-002**: 系统 MUST 保留 codex-candy-eval 的核心评估能力：糖果、指纹、鹈鹕与 SIWC 相关入口/功能；若底层宿主能力不足，必须明确标注降级范围。
- **FR-003**: 系统 MUST 保留原项目的多供应商账户评估能力（OpenAI、Anthropic、Gemini、Antigravity 等），不得因适配 v0.2.21 而缩减为仅支持单一供应商。
- **FR-004**: 系统 MUST 通过最小兼容性变更适配上游版本，变更范围必须可审查、可回退，并附带变更说明。
- **FR-005**: 系统 MUST 提供不依赖 GitHub Actions、云端 CI 或自动部署的本地构建路径，至少能产出 Linux amd64 安装器与服务端二进制。
- **FR-006**: 系统 MUST 提供可重复的安装流程，并在替换失败时自动恢复原 Sub2API 二进制。
- **FR-007**: 系统 MUST 在安装/构建前检查目标平台与架构，不支持的平台必须拒绝产出或拒绝安装。
- **FR-008**: 系统 MUST 不包含任何私有密钥、账号凭据或需要用户保密的构建产物；发布包与源码必须可公开分发。
- **FR-009**: 系统 MUST 在 README 或独立文档中记录：已验证的 Sub2API 版本、构建前置条件、安装步骤、回滚步骤、已知限制。
- **FR-010**: 系统 MUST 保持向后可恢复性：用户从 v0.2.20/v0.2.19 升级到 v0.2.21 后，可按文档重新安装兼容版并恢复评估页面。
- **FR-011**: 系统 MUST 明确排除「GitHub Actions 自动构建/自动发布」作为交付依赖；仓库中可以保留说明，但用户无需启用任何远程工作流即可使用。
- **FR-012**: 系统 MUST 遵守原项目及第三方组件的开源许可证，并在仓库中保留相应版权与许可声明。

### Key Entities *(include if feature involves data)*

- **兼容性版本记录**: 记录上游 Sub2API 版本、codex-candy-eval 版本、验证状态、已知限制；用于回答「哪些版本能用」。
- **构建产物**: 面向目标平台的安装器与服务端二进制；每个产物应有可校验的哈希与目标平台标识。
- **安装记录/备份**: 安装前的原二进制备份、安装后版本信息、回滚所需信息；用于升级失败后的恢复。
- **评估测试结果**: 糖果/指纹/鹈鹕/SIWC 的账户级结果与历史记录；属于原项目业务数据，升级时应尽量保留或提供迁移说明。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在 Sub2API v0.2.21 的测试环境中，按文档完成一次安装，安装成功率达到 100%，且安装后「账户评估」页面可正常打开。
- **SC-002**: 安装后至少能成功执行一次糖果测试并得到明确结果；原有真实 API 请求在测试前后均可正常完成。
- **SC-003**: 从干净源码环境执行本地构建，在文档声明的常规开发机配置下 30 分钟内产出 Linux amd64 安装器与服务端二进制。
- **SC-004**: 兼容性改动相对上游的可审查文件数量占项目总文件数的比例不超过 30%，且每项改动都有说明。
- **SC-005**: 安装失败场景下，100% 能恢复原 Sub2API 二进制并重新通过健康检查。
- **SC-006**: 新用户按 README 从零开始，能在 15 分钟内完成构建前置检查与第一次构建（不含网络下载时间）。
- **SC-007**: 项目文档中明确列出已验证版本与不支持版本；不存在「宣称支持但未验证」的版本记录。

## Assumptions

- 目标 Sub2API 版本为 **v0.2.21**（当前最新 release）；v0.2.22 及以后版本不在本规格承诺范围内，遇到不兼容时应按文档重新评估。
- 目标部署环境为 Linux amd64 服务器，使用 Docker/Compose 或原生可执行文件部署；其他平台仅在文档明确支持的范围内承诺。
- 用户拥有目标服务器的安装权限，并能执行安装器、查看服务日志和回滚。
- 原项目 codex-candy-eval 的功能行为以其自身文档和代码为准；本规格只负责「在 v0.2.21 上恢复这些行为」，不重新定义业务规则。
- 兼容性改动以最小差异为原则，不要求把原项目重写为其他架构。
- 开源分发遵循原项目 LGPL-3.0 及第三方许可证；根目录其他组件按其各自许可证分发。
